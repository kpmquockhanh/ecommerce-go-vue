topic: Auto-generate product variant combinations from option groups, and bulk-update existing variants
updated: 2026-09-07T16:56
---

- (note) Builds on spec-product-options (option groups/values, variant_option_values junction) and spec-product-expansion (variant CRUD). Current CreateVariant/UpdateVariant require admin to submit one combination at a time and a manual unique SKU; no bulk endpoints exist (spec-product-expansion explicitly deferred 'bulk product operations').
- (capability) CAP-1: admin triggers auto-generation of the cartesian product of a product's option group values into variants, skipping combinations that already exist, in one call.
- (decision) SKU is required+unique on ProductVariant today with no auto-fill; auto-generated variants must get a system-generated SKU (product-slug + slugified option values, collision-suffixed) since bulk generation cannot prompt per-combination.
- (constraint) New hard cap of 500 total variants per product, enforced on both generate and manual create, to bound cartesian-product blowup (6 groups x 100 values already allows combinatorial explosion).
- (capability) CAP-2: generation is safe to re-run after option groups change (e.g. new value added) -- only missing combinations are created; existing variants and their stock/SKU are untouched.
- (capability) CAP-3: admin bulk-updates many existing variants (stock, SKU, weight/length/width/height) in a single request via an explicit list of {variant_id, fields}; each item validated and applied independently (non-atomic), response reports per-item success/failure.
- (constraint) Bulk update does not allow changing a variant's option-value combination (recombination stays on the existing single-variant PUT endpoint) -- keeps bulk scope to stock/SKU/dimension edits.
- (constraint) All variant_ids in a bulk update request must belong to the product_id in the path; cross-product IDs are rejected per-item, not fatal to the whole batch.
- (constraint) Bulk generate and bulk update endpoints require the existing admin auth middleware, same as all other admin product/variant endpoints.
- (direction) Non-goal: filter/query-based mass update (e.g. 'set stock=0 for all Red variants') -- only explicit ID-list bulk update is in scope; a selection-by-filter UX can layer on top later without changing this contract.
- (direction) Non-goal: CSV/spreadsheet import-export of variants, cross-product bulk generation, and undo/rollback of a bulk operation -- all deferred.
- (assumption) Auto-generated SKU pattern is '{product-slug}-{option-value-slug-1}-...', lowercase, hyphenated, with a numeric suffix appended on collision -- input gave no explicit SKU convention.
- (assumption) Auto-generated variants default to stock=0 and no weight/dimensions (nullable, matching manual-create defaults) -- admin fills these in afterward via bulk update.
- (question) Open: should generation be blockable/previewable (dry-run showing what would be created) before committing, or is create-directly with a response summary sufficient? Input did not specify; spec assumes direct-create with summary.
- (question) Open: exact per-product variant cap value (500 assumed) is a placeholder pending admin/business confirmation of realistic catalog sizes.
