---
topic: Replace hardcoded size/color variant system with dynamic product options
updated: 2026-09-06T11:16
---

- (direction) User requested review of product customization/options — current system is too simple with hardcoded size/color
- (constraint) Current product_variants has hardcoded size VARCHAR(50) and color VARCHAR(50) columns, no generic option mechanism
- (constraint) product_variants table already exists with sku, stock, weight/dimensions columns that must be preserved
- (constraint) Frontend ProductDetail.vue hardcodes variant display as variant.size / variant.color
- (constraint) Checkout handler hardcodes variant label as Size + ' / ' + Color
- (capability) CAP-1: Admin can define named option groups per product with ordered option values
- (capability) CAP-2: Variants created as combinations of option values via junction table, replacing hardcoded columns
- (capability) CAP-3: Storefront renders dynamic option selectors driven by product option groups
- (capability) CAP-4: Price modifiers per option value adjust displayed and charged price
- (capability) CAP-5: Per-product customization fields (text/textarea/file) with optional price surcharge
- (capability) CAP-6: Variant label computed dynamically from selected option values instead of hardcoded
- (constraint) Max 6 option groups per product, max 100 values per group, max 50 chars per value label
- (constraint) Max 5 customization fields per product, max 500 chars text input, max 10MB file upload
- (constraint) Customization values stored as JSONB on cart_items and order_items
- (constraint) Options are product-scoped, not global templates
- (constraint) Price modifiers are per-option-value, variant effective price is derived
- (decision) Option groups are product-scoped, not global reusable templates
- (decision) No conditional/dependent option groups — all groups independent
- (decision) Stock tracked at variant level, not per-option-value
- (decision) Existing size/color data migrated to option groups, old columns dropped
- (assumption) Existing products with size/color variants will be migrated automatically to new option group model
- (assumption) Frontend variant selector rebuilt as dynamic component driven by option groups API
- (assumption) Customization file uploads use existing S3/MinIO storage infrastructure
- (event) Self-validate Pass 1 (Coherence): All 6 capabilities have intent+success. Intents describe WHAT not HOW. Constraints bend design. Non-goals explicit. Success signal testable. IDs stable.
- (event) Self-validate Pass 2 (Preservation): All source claims (hardcoded size/color, no options, no customizations, rigid variant model) landed in SPEC.md or data-model-changes.md. No wrapper-only content dropped.
- (decision) Story 1: Database migration + option group models + data migration
- (decision) Story 2: Option group + option value admin CRUD (CAP-1)
- (decision) Story 3: Variant CRUD rewrite — option value linkage + computed label (CAP-2, CAP-6)
- (decision) Story 4: Storefront public options endpoint + dynamic display (CAP-3, CAP-4)
- (decision) Story 5: Customization fields admin CRUD + cart/order integration (CAP-5)
- (decision) Story 6: Integration — update all handlers, tests, and cleanup
- (event) stories.yaml written with 6 stories. Validated: all ids unique, prefix-free, required fields present, no status field.
