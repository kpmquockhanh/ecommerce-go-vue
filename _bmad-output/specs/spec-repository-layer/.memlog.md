topic: Move all SQL queries to repository layer
updated: 2026-09-04T18:43
---

- (decision) Repository layer will use interfaces with pgx, injected into handlers via constructor
- (decision) 68 total SQL queries across 10 files, grouped into 9 repository interfaces by entity
- (constraint) Transactions (Checkout, MergeGuestCart, restoreStock) must be handled at repository level, not handler level
- (constraint) Global database.DB remains as connection pool source; repositories receive *pgxpool.Pool via constructor
- (constraint) Dynamic query building (ListProducts filters, AdminListOrders status filter) must be encapsulated in repository
- (non-goal) No ORM引入; keep raw SQL with pgx
- (non-goal) No query builder library; keep hand-written SQL
- (assumption) Handlers will depend on repository interfaces, not implementations
- (capability) CAP-1: UserRepository handles all user-related queries (register, login, profile, admin list)
- (capability) CAP-2: ProductRepository handles product CRUD, listing with filters, variants, and review stats
- (capability) CAP-3: CartRepository handles cart CRUD for users and guests, including merge transaction
- (capability) CAP-4: OrderRepository handles checkout transaction, order listing, and admin order management
- (capability) CAP-5: ReviewRepository handles review creation with ON CONFLICT, listing with pagination
- (capability) CAP-6: IdempotencyRepository handles checkout idempotency key lookups and storage
- (capability) CAP-7: DeadLetterRepository handles DLQ listing, retry, and delete
- (capability) CAP-8: WebhookRepository handles order lookup by payment intent and status updates
- (capability) CAP-9: StockRepository handles stock locking (FOR UPDATE) and decrement/increment for checkout and restore
- (event) Spec created: 9 repository interfaces covering 68 SQL queries, companion with full interface definitions and wiring plan
