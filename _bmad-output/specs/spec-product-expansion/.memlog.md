topic: Expand e-commerce product creation/modification with multiple categories and enhanced product features
updated: 2026-09-05T23:12
---

- (direction) User wants to expand product creation/modification with multiple categories and other e-commerce enhancements
- (constraint) Current products.category is a VARCHAR, not FK. product_variants table exists but has no API endpoints. No public category listing.
- (capability) CAP-1: Many-to-many product-category relationship. Admin can assign multiple categories to a product. Products filterable by multiple categories.
- (capability) CAP-2: Variant CRUD endpoints. Admin can create, update, delete product variants (size, color, stock, SKU) via API.
- (capability) CAP-3: Public category listing. Storefront can list all categories with product counts for navigation.
- (capability) CAP-4: Product tags. Admin can assign multiple tags to products for flexible filtering beyond categories.
- (capability) CAP-5: Sale pricing. Products support a compare_at_price field for displaying original vs sale price.
- (capability) CAP-6: Product status lifecycle. Products have status (draft/published/archived) instead of just active boolean.
- (capability) CAP-7: Product weight and dimensions. Products store weight, length, width, height for shipping calculations.
- (capability) CAP-8: SEO metadata. Products support meta_title, meta_description, og_image for search engine optimization.
- (capability) CAP-9: Product image ordering. Admin can set primary image and order for product images.
- (assumption) Assumed backward compatibility: existing single-category products will migrate to the new many-to-many table
- (assumption) Assumed variant CRUD is admin-only, consistent with existing product management endpoints
- (assumption) Assumed tags are simple string labels, not a separate hierarchical entity
- (question) Should product status replace the active boolean or coexist? (draft/published/archived vs active flag)
- (question) Should weight/dimensions be at product level or variant level (different sizes have different weights)?
- (question) Should bulk product operations (bulk create/update/delete) be included in this expansion?
- (event) Self-validate Pass 1 (Coherence): All 9 capabilities have intent+success. Intents describe WHAT not HOW. Constraints bend design decisions. Non-goals are explicit. Success signal is testable. IDs stable.
- (event) Self-validate Pass 2 (Preservation): All source claims from user request (multiple categories, product expansion) landed in SPEC.md or data-model-changes.md companion. No wrapper-only content dropped.
- (decision) status fully replaces active boolean. active column dropped, not deprecated.
- (decision) Weight/dimensions at both product and variant level. Variant values override product's when present (for shipping calc).
- (decision) Bulk product operations deferred to future expansion.
- (decision) Max 12 tags per product. Validation enforced in handler.
- (event) Spec updated with resolved decisions: active dropped, variant-level weight/dimensions, bulk deferred, max 12 tags. All open questions resolved.
- (decision) No backward compatibility required. Fresh migration — drop old columns, create new tables clean. No gradual transition.
- (event) Spec updated: fresh migration approach. All IF NOT EXISTS removed, old columns dropped clean, no gradual transition.
- (decision) Story 1: Database migration + multiple categories (CAP-1) + public category endpoint (CAP-3)
- (decision) Story 2: Variant CRUD endpoints (CAP-2)
- (decision) Story 3: Product tags (CAP-4) + sale pricing (CAP-5)
- (decision) Story 4: Product status lifecycle (CAP-6) + weight/dimensions (CAP-7)
- (decision) Story 5: SEO metadata (CAP-8) + image ordering (CAP-9)
- (decision) Story 6: Integration — update existing handlers/repos to new schema, update list/detail responses
- (event) stories.yaml written with 6 stories. Validated: all ids unique, prefix-free, required fields present, no status field.
